## Purpose

Spec for the split-tunnel-router capability: a sing-box-based router on
`fedorivns-mbp` and `fedorivns-homelab` that sends corp domains
(`*.tcsbank.ru`, `*.t-tech.team`) through the corp-proxy-bridge SOCKS endpoint
and all other traffic through subscription proxy nodes, using FakeIP and DNS
hijacking so domain-based routing applies to all applications.

The corp overlay applies to `fedorivns-mbp` only; the homelab runs the base
profile.

## Requirements

### Requirement: Default traffic via subscription proxy

The router SHALL send all traffic that does not match a more specific rule to
a `proxy` selector backed by subscription nodes. Non-corp traffic MUST NOT
traverse the corp proxy bridge.

The personal WireGuard endpoint (`snejugal.ru`) is banned as a general exit and
MUST NOT be the default outbound. It SHALL remain configured for peer-to-peer
traffic and SHALL remain selectable as a manual fallback.

#### Scenario: Generic traffic exits via a subscription node

- **WHEN** the router is running and `curl https://ifconfig.me` is executed on
  `fedorivns-mbp`
- **THEN** the observed egress IP belongs to one of the subscription nodes,
  not the local ISP, not the WireGuard endpoint and not the corp laptop

#### Scenario: Fastest node is chosen automatically

- **WHEN** the router starts with more than one subscription node available
- **THEN** a `urltest` group selects among them by latency, and the `proxy`
  selector defaults to that group

#### Scenario: WireGuard still carries peer traffic

- **WHEN** traffic is destined for `10.6.6.0/24` or `fd9f:6666::/64`
- **THEN** it is routed to the `wg` endpoint, not to the subscription nodes
  and not direct

### Requirement: Corp domains routed via the proxy bridge

The router SHALL route connections to `*.tcsbank.ru` and `*.t-tech.team`
through the `corp-proxy-bridge` SOCKS endpoint (`127.0.0.1:1080`).

#### Scenario: Corp host is reachable through the router

- **WHEN** the bridge is up and `curl https://wiki.tcsbank.ru` or
  `curl https://copilot.t-tech.team` is executed with no explicit proxy
- **THEN** the corp-internal host responds

#### Scenario: Corp connection is tagged to the bridge outbound

- **WHEN** a `*.tcsbank.ru` or `*.t-tech.team` connection is opened
- **THEN** the router logs show it routed to the corp SOCKS outbound, not the
  WireGuard outbound

### Requirement: FakeIP resolution for corp domains

The router SHALL resolve `*.tcsbank.ru` and `*.t-tech.team` using FakeIP,
returning a placeholder address from a reserved range and deferring real name
resolution to the corp laptop via the SOCKS bridge. It MUST NOT depend on
querying the corp resolver directly from the Mac (the corp resolver is
UDP-only and unreachable over the TCP-only SOCKS path).

#### Scenario: Corp domain resolves to a FakeIP

- **WHEN** `fedorivns-mbp` resolves `wiki.tcsbank.ru` or
  `copilot.t-tech.team` while the router is running
- **THEN** the returned address is within the configured FakeIP range
  (`198.18.0.0/15`)

#### Scenario: Real resolution happens at the corp side

- **WHEN** a connection to the FakeIP for a corp domain is initiated
- **THEN** the router passes the original hostname to the SOCKS bridge, and
  the corp laptop performs the actual DNS resolution

### Requirement: DNS is hijacked by the router

The router SHALL intercept system DNS queries so that domain-based routing and
FakeIP take effect for all applications, not only those configured with an
explicit resolver.

#### Scenario: DNS queries are captured

- **WHEN** any application on `fedorivns-mbp` issues a DNS query while the
  router is running
- **THEN** the query is handled by the router's DNS rules rather than going
  directly to an external resolver

### Requirement: Private and non-corp DNS unaffected

The router SHALL route private/RFC1918 destinations directly and SHALL resolve
non-corp domains via the resolver reached through the default outbound, leaving
normal name resolution intact.

#### Scenario: Private addresses bypass both tunnels

- **WHEN** traffic is destined for a private (RFC1918) address
- **THEN** it is routed directly, not through WireGuard or the corp bridge

#### Scenario: Non-corp names resolve normally

- **WHEN** a domain outside `tcsbank.ru` and `t-tech.team` is resolved
- **THEN** it is resolved via the default (proxy-side) resolver and is not
  assigned a FakeIP

### Requirement: Configuration generated by nix with sops secrets

The sing-box configuration SHALL be generated from a nix-managed template on
every host running the router, with the WireGuard `private_key` and
`pre_shared_key`, the subscription URL, and the subscription node definitions
all sourced from sops. No such secret SHALL be committed in cleartext or be
left world-readable, and none SHALL reach the Nix store.

#### Scenario: No cleartext keys in the repo

- **WHEN** the repository tree is inspected after this change
- **THEN** no WireGuard `private_key` or `pre_shared_key` appears in cleartext
  (the untracked root `singbox.json` is gone; keys live in `secrets.yaml`)

#### Scenario: Subscription nodes are not in the Nix store

- **WHEN** the generated profile is inspected in the Nix store
- **THEN** the node credentials appear only as a sops placeholder, and the real
  values exist solely in the activation-time rendered file

#### Scenario: Node identities are not in the Nix store either

- **WHEN** the store-resident template is searched for node tags, the provider
  name or server addresses
- **THEN** none appear — the proxy group is defined inside the secret, so the
  store sees only `direct`, `wg` and `proxy`

#### Scenario: Both hosts render the same way

- **WHEN** the mac and the homelab profiles are generated
- **THEN** both come from the shared `lib/sing-box/render.nix` splice, and
  neither relies on `services.sing-box.settings` secret substitution

#### Scenario: Rendered config is not world-readable

- **WHEN** the generated config containing the decrypted keys exists on the
  activated host
- **THEN** its file permissions restrict read access to the owning user (the
  invoking user on the mac, the `sing-box` service user on the homelab)

### Requirement: Configuration validated before activation

Each generated profile SHALL be checked against a real sing-box binary at build
time, using dummy values in place of secrets, so a schema error fails the build
rather than the service.

#### Scenario: A malformed profile fails the build

- **WHEN** a generator change produces a profile sing-box rejects
- **THEN** the corresponding `sing-box-check-*` derivation fails and the host
  does not build

Note: `sing-box check` validates shape only. Detour resolution happens at
service start, so a detour to an option-less `direct` outbound passes the check
and is still fatal at runtime.

### Requirement: Subscription nodes refreshable without hand-editing

The capability SHALL provide a repeatable command that re-fetches the
subscription and writes the node definitions back into `secrets.yaml`, so a
provider-side node change does not require editing encrypted YAML by hand.

#### Scenario: Refresh updates the stored nodes

- **WHEN** `just refresh-sing-box-subscription` is run
- **THEN** the current node set is fetched and stored encrypted under
  `sing-box/proxy-outbounds`, together with the `proxy-auto` urltest and
  `proxy` selector built over it

#### Scenario: Empty fetch does not destroy the stored nodes

- **WHEN** the subscription returns no usable nodes
- **THEN** the command aborts non-zero and leaves the previous value in place
